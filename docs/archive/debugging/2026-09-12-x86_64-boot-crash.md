# x86_64 early boot crash: large-model orphan sections

## Root cause

The failure after `EFER: NXE enabled` occurs before AP startup and is not
specific to SMP. The x86_64 linker script did not collect `.ldata` and
`.lbss`, emitted by the large code model. LLD placed these orphan sections
after the linker-defined `_end` symbol. PMM uses `_end` as `start_brk`, so
its bitmap and page/zone metadata occupied live kernel data.

The failing image inspected during this investigation had:

| Item | Virtual address |
| --- | --- |
| `_end`, start of orphan `.ldata` | `0xffff8000002a8000` |
| Start of orphan `.lbss` | `0xffff8000002b3380` |
| `PMMngr` | `0xffff8000002b5ec8` |
| Actual end of allocated sections | `0xffff8000002cf130` |

`pmm_init` clears metadata allocated from `_end`; the clearing overlaps
`PMMngr` itself. Later bitmap accesses use corrupted pointers. QEMU's first
page fault was at `pmm_init`, with `RDX=0` and `CR2=0x000000ffff800000`,
followed by recursive faults. This explains why added diagnostic prints
changed the symptom: layout changes alter which globals get overwritten.
The initial disk contained old diagnostic prints despite clean source;
`make PROFILE=x86_64-clang disk.img` rebuilt it from current source.

## Fix

Collect large-model data and BSS explicitly inside the existing output
sections, before `_end`. Include ordinary/large-model text and rodata
subsections in their respective boundary symbols as well. Preserve the
separate, 32 KiB-aligned `.data.init_task` output section.

After relinking, the inspected ELF has `PMMngr=0xffff8000002b2b48` and
`_end=0xffff8000002cbdb0`: PMM metadata starts beyond all kernel globals.
No C struct or UAPI changes are involved.

## Regression checks

`make PROFILE=x86_64-clang test-kernel-layout` inspects the actual ELF,
checking that every allocated section ends before `_end`, all NOBITS
sections lie within BSS bounds, and code/read-only sections are within
their declared bounds. The test failed on the original ELF and passed
with the linker fix.

Validation performed:

- Normal 512 MiB QEMU boots with one and four vCPUs reach BusyBox ash;
  both execute a serial-injected printf command and return the expected
  CPU-count-specific marker.
- `make PROFILE=x86_64-clang test`: 17 suites, zero failures.
- `make PROFILE=x86_64-clang OS01_SYSTEST=1 test-syscall`: 268 passed,
  zero failed. This harness runs one vCPU and no kernel selftests.

## Separate PMM issues found during investigation

These are not changed by this narrowly scoped linker fix and require
separate allocator tests:

- `kernel/arch/x86_64/pmm_arch.c` computes the E820 type but emits every
  surviving range as `MEMORY_TYPE_RAM`, then merges without checking type.
  Reserved/MMIO ranges can therefore be advertised as allocatable RAM.
- `MEMORY_RANGE_GRANULE` is a 32-bit constant; complement masks in
  `pmm_init` truncate addresses above 4 GiB.
- `pmm_init` uses RAM-relative bitmap indexes, while allocation/free bitmap
  updates still use absolute physical-page indexes. A nonzero RAM base
  needs explicit coverage.

The current boot result establishes the cause of this early crash; it
is not a claim that these independent PMM issues are safe under other
memory maps or sustained memory pressure.
