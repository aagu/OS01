### 2.5 PTY slave devfs 节点泄漏（x86 E2E 的"永久化"机制）

**失败测试**：`make test-qemu SUITE=phase-0 QEMU_SMP_MATRIX="1 2"` → `FAIL: No shell prompt`
**引入 commit**：不在本次回归区间——这是**长期存在的缺陷**，只是被新的 CI 工具链产物触发。

**根因**（`kernel/tty/pty.c`）：

```c
static int ptmx_open(const char *name, file_t **out_file)
{
    ...
    // 每次打开 /dev/ptmx 都注册一次 slave 节点
    devfs_register_chrdev(slave_name, pty, &pty_slave_ops);
    ...
}
```

`kernel/fs/devfs.c` **没有任何 unregister API**。`devfs_register_node()` 在叶子名
已存在时返回 `-EEXIST`（约 1014-1016 行）。

于是：

1. terminal 第一次打开 `/dev/ptmx` → 注册 `/dev/pts0` → 成功；
2. terminal 退出，`pty_table[0]` 的 slot 被释放（`kernel/fs/file.c:136-152`：
   `master_without_slave = (f->type == FD_PTY_MASTER) && !pty->slave_opened`）；
3. init respawn terminal → 再次打开 `/dev/ptmx` → 复用同一个 index 0 →
   再次注册 `/dev/pts0` → **`-EEXIST`** → `ptmx_open` 失败 →
   `open("/dev/ptmx")` **永久失败**。

**用户可见后果**：`user/terminal/terminal.c:198-215` 第 8 步
`open("/dev/ptmx", O_RDWR)` 失败即打印
`[terminal] ERROR: open /dev/ptmx failed` → `exec(shell)` → `return 1`。
init 反复 respawn，串口上刷出成百上千条同样的错误，永远等不到 shell 提示符。

**修复**（`kernel/tty/pty.c`）：**一次性预注册** slave 节点。

- 新增静态辅助 `pty_slave_name(buf, index)`，统一生成 `"pts0" … "pts7"`。
- `pty_init()` 一次性注册 `pts0..pts7`（`PTY_MAX == 8`），并绑定 `&pty_table[i]`。
  节点是**永久绑定**：`/dev/pts{N}` 永远指向 `&pty_table[N]`。
- `ptmx_open()` 不再触碰 devfs（删掉整段注册 + 回滚代码）。
- `ptsN_open()` 改用 `pty_slave_name()` 复用同一命名逻辑。

**用户可见语义不变**：打开一个 slot 尚未分配的 slave，仍然返回 `-ENOENT`
（`ptsN_open()` 里 `if (!pty_table[i].allocated) continue;` 的逻辑未动），
改变的只是节点的**生命周期**，不是可见行为。

**为什么选这个方案**（而不是别的）：
- 不给 devfs 加 unregister API——改动面大，且 devfs 节点生命周期理应与静态 slot 绑定一致；
- 不把 `-EEXIST` 当成功——那会掩盖真实的重复注册；
- 一次性预注册是改动面最小、语义最清晰的做法。

**验证**：
- 新增回归测试 `hosttests/cases/test_pty_winsize.c::test_ptmx_reopen_after_master_release`：
  打开 master → 释放 → **重新打开**（旧代码此处返回 `-EEXIST`）。
  该文件的 devfs mock 同时升级为"能返回 `-EEXIST` 的注册表模型"（原来只会成功）。
- **mutation**：把 `kernel/tty/pty.c` 还原成旧行为 → 新测试**干净失败**并报
  `rc=-17`（`-EEXIST`）；恢复修复 → 通过。
- `hosttests/cases/test_boot_failure_terminal.c`：devfs mock 增加 `pts0..7` 分支
  （返回 0、计数 `registered_pts_calls`），`test_pty_init_success` 断言
  `PTY_MAX == registered_pts_calls`（防止预注册条数漂移）。
- **端到端证实**（决定性证据）：
  - 用 CI 构建的 `disk.img`（artifact `x86_64-disk-image`）在本地 QEMU 复现出
    **完全相同**的失败（`ptmx_err=336`，无 shell prompt）；
  - 只把内核换成我方（含本修复）的 `kernel.bin` 后 → **`ptmx_err=0`**，
    "open /dev/ptmx failed" 风暴消失。

### 3.4 挂死本身尚未定性（建议接手者优先处理）

`qemutests/run_framework_tests.py` 的 `run_module()` 用**非阻塞**管道读子进程输出：

```python
os.set_blocking(proc.stdout.fileno(), False)
...
data = stream.read()
if not data:
    reads.remove(stream)   # ← 任何一次"空读"都被当成 EOF
```

如果某次 `select` 报可读、但 `read()` 返回空串（例如 EAGAIN 竞态），该 fd 会被
**误判为 EOF 并移出监视列表**；子进程随后往写满的管道里写剩余输出 → 阻塞 →
600s 后被杀。

**这只是假设，没有确认。** 我用 3 MB 的单次大写入做过压力复现，`read()` 正常返回
全部数据（3000000/3000000），**没有**复现出空读。所以还有别的因素（CI 容器的
内存/CPU 压力？unittest 失败块的输出量？）。

**一个重要的对照数据**：本地跑同一个 `qemutests.test_boot_irq_time` 模块，
`status=PASS duration=0.12s`——**同一个模块在本地根本不挂**。注意这里有一个
关键的不对称：本地（修复后）**PASS**，根本不打印失败块，输出量极小；而 CI 上
该模块 **FAIL**，要打印一个包含**整份 `kernel/Makefile` 文本**的
`AssertionError`（`assertIn` 把 haystack 全文塞进消息里），输出量比成功路径大
几个数量级。

⇒ 这与"**大输出 + 非阻塞读**"的假设方向一致，但**不能证明**：修复后本地不再
产生那段大输出，因此这个对照**无法区分**"输出量"与"CI 运行环境"两个变量。
要区分，需要在 CI 上重跑（此时该模块已 PASS、输出变小——如果不再挂，就能证明
是输出量；如果照样挂，就是环境问题）。**这恰好是本变更推上 CI 后能顺带得到的
免费信息**，请接手者优先看 CI 上 framework job 是否还挂。

**建议的定位步骤**（接手者）：
1. 在 `run_module()` 里把 `if not data:` 改成只在 `stream` 真正 EOF 时才移除
   （用 `stream.read1()` 或显式 `os.read` + `EAGAIN` 重试），看 600s 挂死是否消失。
2. 给 `run_module()` 加一条"子进程已退出但输出未读完"的诊断日志。
3. 无论如何，**runner 不应在单个模块超时后静默丢失后续 57 个模块的结果**——
   建议在超时后仍然打印 summary，并给 CI 一个明确的"模块超时"状态。

## 4. 遗留问题：x86 E2E 的**触发**根因未定性

### 4.1 已确定的事实

CI run 45005873953 与 45003829685 的串口序列**完全一致**：

```
boot1: [boot-2] context-ready …
       init: started pid 2: '/bin/terminal'
       ← guest 静默 reset（无 panic、无 PF-KRN 字样）
boot2: fork: pid=2 returned 3
       init: pid 2 (/bin/terminal) exited, status=0
       ← init 反复 respawn，每次都是：
       [terminal] ERROR: open /dev/ptmx failed
       ← [TEST] TIMEOUT waiting for pattern: #
FAIL: No shell prompt
```

- terminal **以 status=0 正常退出**（`user/init.c:130`），不是被信号杀死；
- **busybox 的 banner 从未出现**——shell 根本没跑到能打印 banner 的程度；
- `open /dev/ptmx failed` 风暴 = §2.5 的 PTY 泄漏，**已修复**。

### 4.2 修复 §2.5 之后仍然存在的现象

把我方（含 PTY 修复的）内核换进 CI 构建的 `disk.img`：

- `ptmx_err` 从 336 → **0**（失败风暴消失）；
- 但 terminal **仍然以 status=0 退出**，**仍然没有 shell 提示符**，busybox banner
  **依旧没有出现**。

⇒ PTY 泄漏是**放大器**（把一次瞬时失败变成永久失败），不是**触发器**。
真正的触发器在别处。

### 4.3 已排除的方向（避免接手者重复劳动）

- **不是** fb geometry：两个镜像完全一致（`w=1440 h=900`）。
- **不是** mmap 长度：两个镜像完全一致（`len=5185536`，`sizeof(fb_state)=32`）。
- **不是** fault 模式差异：terminal 的逐页 demand fault 两镜像一致；ash 只有 1 次
  COW fault（地址 `link+0xD000`），两镜像相同。
- **不是** PTY 泄漏本身（见 §4.2）。

> 注：上述数据由临时插桩测得，**插桩代码已全部回滚**，不在本次变更里。

### 4.4 最有嫌疑的方向

**CI 工具链产出的用户态二进制触发了内核的一个潜在缺陷**——同一份源码在本地
工具链（clang 23.1.5 / qemu 11.1.3）构建的 `disk.img` **不复现**，只有 CI 构建的
镜像复现。二进制差异：

| | CI | 本地 |
|---|---|---|
| busybox | 348184 B | 348168 B |
| kernel.bin | 851968 B | 851976 B |
| busybox 属性 | ET_DYN，entry `0xf0`，3 phdr，236 个 `R_X86_64_RELATIVE` | 同 |

回归区间 `dfe88919..8fa531ae` 里的 **static-PIE / ASLR 系列**提交与上述特征
（ET_DYN + 大量 `R_X86_64_RELATIVE`）高度吻合：

| commit | 内容 |
|---|---|

具体怀疑点（**均未确认**）：

1. `kernel/arch/x86_64/fs/elf.c:331-350` —— PIE 的 `R_X86_64_RELATIVE` 打补丁循环：

   ```c
   dst_va = bias + r_offset;
   pte = vmm_pt_walk(...);
   pa = x86_pte_4k_pa(*pte);      // ← *pte 没有 NULL 检查
   val = bias + r_addend;
   ```

   `*pte` 无 NULL 检查。boot-1 的**静默 triple fault**（无 panic 字样）疑似与此有关。

2. `kernel/arch/x86_64/memory/aslr.c` 的 `x86_aslr_get_pie_bias()`：
   `bias = X86_USER_PIE_BIAS_BASE(0x400000) + ((raw & 0xFFFF) << 12)`。
   CI 的 RNG 流与本地不同 → bias 不同 → 不同的地址落点，可能撞上某个边界条件。
   窗口常量见 `kernel/include/arch/x86_64/user_layout.h`。

### 4.5 为什么难以定位：两条静默路径在串口上不可区分

`user/terminal/terminal.c` 里至少有两条"什么都不打印就退出"的路径：

- `terminal.c:428-432` —— `poll()` 返回 <0 且非 EINTR → `break`；
- `terminal.c:501-523` —— pty master read 返回 0/错误 → `shell_exited` → `break`；
- 结尾 `return 0`（第 539 行）。

两条路径在串口日志上**都不留痕迹**——这是卡点。

**建议接手者的第一步**：在这两处各加一条 `log_warn`（AGENTS.md 要求用
`log_warn/log_err`，不要用 `serial_printk`/`color_printk`），把 `poll()` 的返回值、
`errno`、master read 的返回值打印出来。这两条日志能一次性区分两条路径，
是当前性价比最高的一步。

## 7. 复现与二分命令

```bash
# ① 下载 CI 产物
#    artifact x86_64-disk-image → /tmp/ci-disk/disk.img
#    artifact x86-test-logs    → build/*/logs/tests/**

# ② 用 CI 参数复现
qemu-system-x86_64 -M q35 \
  -drive if=pflash,format=raw,readonly=on,file=build/x86_64-clang/firmware/OVMF.fd \
  -drive file=/tmp/ci-disk/disk.img,format=raw,if=none,id=disk \
  -device ahci,id=ahci -device ide-hd,drive=disk,bus=ahci.0 \
  -object rng-random,filename=/dev/urandom,id=rng0 -device virtio-rng-pci,rng=rng0 \
  -m 512 -smp 1 -serial file:/tmp/serial.log -display none -no-reboot -no-shutdown
# 判定：boots / "open /dev/ptmx failed" 计数 / "^# " 计数

# ③ 替换内核做二分（FAT ESP 内的文件名必须是 kernel.bin）
mcopy -o -i /tmp/boot.img <local>/build/x86_64-clang/image/rootfs.next/kernel.bin ::/kernel.bin
dd if=/tmp/boot.img of=/tmp/new.img bs=512 seek=2048 count=131072 conv=notrunc
```

### 踩坑记录

- **`mcopy` 写 FAT 分区**：必须指定完整目标名 `::/kernel.bin`。写成 `::/kernel`
  会**新建**一个无扩展名的文件，OVMF 随后报 "failed to load Boot0002"。
- **`pkill -f qemu-system-x86_64` 会误杀自身 shell**（命令行含该字符串）→
  改用 `pkill -x` 或先拿 PID 再 `kill`。
- **QEMU 采集串口**：`-serial stdio` 在 stdin 非 TTY 时可能无输出，
  用 `-serial file:/tmp/serial.log` 更可靠。
- **`debugfs -w`**（ext2 原地写入）被宿主权限网关拦截；FAT 分区用 mtools 可写。
- **临时诊断插桩已全部回滚**：`kernel/arch/x86_64/intr/trap.c`（user-pf 日志）、
  `kernel/driver/fb.c`（fbstate 日志）、`kernel/arch/x86_64/memory/mmap.c`
  （mmap 日志 + `#include <log/log.h>`）均已 `git checkout --` 还原。
